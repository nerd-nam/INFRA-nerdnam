# 5단계 데이터 계층 (PostgreSQL·Redis·PVC)

기준일: 2026-10-28. 상태: **코드·로컬 검증 완료, 미배포.** 이 문서의 "확인함"은 로컬 Helm 렌더링과 로컬 Docker 실행 결과다. EKS 노드 위 실행, EBS PVC 재연결, NetworkPolicy 실제 차단, ExternalSecret 동기화는 배포 후 검증할 항목이다.

범위 밖(보류): PostgreSQL S3 일일 백업, 새 PVC 복원 시험, 백업 bucket·CronJob·IAM·snapshot. exporter(7단계), BE Deployment(6단계).

## 1. 구성

| 항목 | PostgreSQL | Redis |
| --- | --- | --- |
| 이미지 | `pgvector/pgvector:0.8.7-pg17-bookworm@sha256:ac08538c…a75d` (PG 17.11, pgvector 0.8.7) | `redis:7.4.12-alpine@sha256:338fbfc0…66e2` |
| 객체 | StatefulSet 1 / replica 1, `postgres-headless`(Pod DNS), `postgres`(ClusterIP) | StatefulSet 1 / replica 1, `redis-headless`, `redis`(ClusterIP) |
| 접속 주소 | `postgres.data.svc.cluster.local:5432`, DB `nerdnam` | `redis.data.svc.cluster.local:6379` |
| PVC | `data-postgres-0`, gp3-retain 30Gi, RWO | `data-redis-0`, gp3-retain 5Gi, RWO |
| 실행 사용자 | uid/gid 999, fsGroup 999 | uid 999 / gid 1000, fsGroup 1000 |
| 자원 | requests 750m / 2Gi, limit 메모리 3Gi | requests 250m / 512Mi, limit 메모리 768Mi |
| 종료 | preStop `pg_ctl stop -m fast -W`, grace 120초 | SIGTERM(AOF fsync 후 종료), grace 60초 |

- 두 이미지 digest는 multi-arch index digest다(Docker Hub에서 2026-10-28 조회). amd64 워커에서 맞는 manifest를 고른다.
- Redis 7.4부터 라이선스가 RSALv2/SSPLv1이다. 내부 세션 저장소 용도로는 문제가 없지만 버전 기준을 바꿀 때 함께 검토한다.
- 모두 `workload=data` nodeSelector + `dedicated=data:NoSchedule` toleration. root 파일시스템 읽기 전용, capability 전부 제거, ServiceAccount token·service link 환경 변수 없음.
- CPU limit은 두지 않는다(DB 스로틀링 방지). 메모리 limit만 둔다. data 노드(m7i.large 8GiB)에서 두 limit 합은 3.75Gi다.
- PostgreSQL 설정(시작값): `max_connections=40`, `shared_buffers=512MB`, `effective_cache_size=1536MB`, `work_mem=8MB`, `maintenance_work_mem=256MB`(HNSW 색인 생성), 1초 이상 쿼리 로그. `/dev/shm`은 메모리 emptyDir 256Mi(메모리 limit에 포함).
- `PGDATA=/var/lib/postgresql/data/pgdata`: EBS 루트의 `lost+found` 때문에 하위 디렉터리를 쓴다.
- initdb: `--data-checksums --auth-local=peer --auth-host=scram-sha-256`. 컨테이너 안 TCP 접속도 비밀번호가 필요하다.
- data namespace에 ResourceQuota(LoadBalancer·NodePort 0개, PVC 4개, storage 60Gi 등)와 LimitRange 기본값을 둔다.

## 2. PostgreSQL 역할과 Flyway 책임

`vector` 확장은 trusted가 아니어서 슈퍼유저만 만들 수 있다(이미지에서 확인). 그래서 확장과 역할은 최초 초기화가 맡고, 업무 스키마는 계속 BE Flyway가 맡는다.

| 역할 | 권한 | 사용처 |
| --- | --- | --- |
| `postgres` | 슈퍼유저 | 초기화 스크립트, 운영 작업(확장 업그레이드 등). nerdnam namespace에 주지 않는다 |
| `nerdnam_migrator` | DB `nerdnam` 소유자, app/rag 스키마·테이블 소유 | BE Flyway (`SPRING_FLYWAY_USER`) |
| `nerdnam_app` | CONNECT + default privileges로 받은 스키마 USAGE, 테이블 DML, 시퀀스 USAGE/SELECT | BE 런타임 (`SPRING_DATASOURCE_USERNAME`) |

- 초기화 스크립트는 `gitops/data/files/postgres-init.sh`, ConfigMap `postgres-init`으로 `/docker-entrypoint-initdb.d`에 들어간다. **빈 데이터 디렉터리로 처음 시작할 때만 실행된다.**
- 스크립트가 하는 일: 두 역할 생성, DB 생성(소유자 migrator), PUBLIC의 DB 접근 제거, `postgres` DB의 PUBLIC CONNECT 제거, `vector`·`pg_trgm` 확장 생성, migrator가 앞으로 만드는 객체에 대한 app의 default privileges.
- BE V1 migration의 `CREATE EXTENSION IF NOT EXISTS`는 이미 있는 확장이라 건너뛴다. `CREATE SCHEMA IF NOT EXISTS app/rag`는 DB 소유자인 migrator가 실행한다.
- 현재 BE는 앱 시작 시 Flyway를 돌리므로 migrator 비밀번호도 BE Pod에 들어간다. 전용 migration Job을 도입하면 그때 BE에서 `SPRING_FLYWAY_*`를 뺀다.
- app은 `app.flyway_schema_history`에도 DML 권한을 받는다(default privileges가 테이블 전체에 적용). 필요하면 그 테이블만 REVOKE한다.

## 3. Redis

- 설정: `gitops/data/files/redis.conf`. AOF `everysec`(RDB preamble), 별도 RDB 스냅샷 없음, `maxmemory 256mb`, `noeviction`(꽉 차면 쓰기 거부 → 7단계 알림 대상).
- 인증은 ACL: `default` 사용자 끔, `api` 사용자만 사용. 키는 `nerdnam:*`(BE 세션 키 `nerdnam:session:...`), 명령은 `+@all -@dangerous +info`(actuator Redis health가 `INFO`를 쓴다).
- 시작 스크립트(`files/redis-start.sh`)가 메모리 볼륨 `/run/redis/users.acl`에 비밀번호의 SHA-256 해시만 쓴다. 평문은 디스크에 남지 않는다.
- probe는 `redis-cli --user api ping`, 비밀번호는 `REDISCLI_AUTH` 환경 변수로 넘긴다(명령줄에 노출하지 않음).
- BE가 `nerdnam:` 밖의 키를 쓰는 캐시를 추가하면 ACL 키 패턴을 함께 바꿔야 한다. exporter 사용자는 7단계에서 따로 추가한다.

## 4. 비밀값 키 계약

Secrets Manager `nerdnam/dev/data`(JSON)가 DB·Redis 인증의 단일 출처다. 값은 Terraform·Git 밖에서 공급한다.

| JSON 키 | data namespace (`data-secrets`) | nerdnam namespace (`backend-secrets`) |
| --- | --- | --- |
| `postgres-superuser-password` | PostgreSQL `POSTGRES_PASSWORD` | 주지 않음 |
| `postgres-migrator-password` | 초기화 때 migrator 비밀번호 | `SPRING_FLYWAY_PASSWORD` |
| `postgres-app-password` | 초기화 때 app 비밀번호 | `SPRING_DATASOURCE_PASSWORD` |
| `redis-api-password` | Redis ACL `api` 비밀번호, probe | `SPRING_DATA_REDIS_PASSWORD` |

- `backend-secrets`는 기존대로 `nerdnam/dev/backend` 전체를 받고(`dataFrom`), 위 세 키만 `nerdnam/dev/data`에서 골라 Spring 환경 변수 이름으로 추가한다(`data`). `nerdnam/dev/backend` JSON에는 이 세 Spring 키를 넣지 않는다.
- 권장 값: 32자 이상 무작위 문자열. 줄바꿈만 아니면 따옴표·공백도 동작한다(로컬에서 `'`·`"`·공백·`$` 포함 값으로 확인).
- **회전**: 초기화 뒤에는 Secret 값을 바꿔도 DB·Redis가 따라 바뀌지 않는다(Redis는 Pod 재시작 때 새 해시를 쓴다). PostgreSQL은 슈퍼유저로 `ALTER ROLE … PASSWORD`를 먼저 실행한 뒤 Secrets Manager 값을 바꾸고, ESO 갱신(1시간 주기 또는 수동) 후 BE를 재시작한다. Redis는 값을 바꾼 뒤 Redis와 BE를 함께 재시작한다(세션은 AOF에 남는다).

## 5. BE(6단계)가 맞춰야 할 설정

| 환경 변수 | 값 |
| --- | --- |
| `SPRING_PROFILES_ACTIVE` | `prod` 등 local이 아닌 값 (default는 local이라 시드·헤더 인증이 켜진다) |
| `SPRING_DATASOURCE_URL` | `jdbc:postgresql://postgres.data.svc.cluster.local:5432/nerdnam` |
| `SPRING_DATASOURCE_USERNAME` | `nerdnam_app` |
| `SPRING_DATASOURCE_PASSWORD` | `backend-secrets` |
| `SPRING_FLYWAY_USER` | `nerdnam_migrator` |
| `SPRING_FLYWAY_PASSWORD` | `backend-secrets` |
| `REDIS_HOST` / `REDIS_PORT` | `redis.data.svc.cluster.local` / `6379` |
| `SPRING_DATA_REDIS_USERNAME` | `api` |
| `SPRING_DATA_REDIS_PASSWORD` | `backend-secrets` |

- BE Pod 라벨은 `app: api`여야 한다(`gitops/data/values.yaml`의 `apiPodLabels`). 라벨이 다르면 NetworkPolicy가 DB 접근을 막는다.
- HikariCP 기본 풀 10개 × BE 1 replica + Flyway 연결 < `max_connections=40`. replica나 풀을 늘리면 함께 본다.
- BE 코드 변경은 필요 없다. Spring Boot가 위 환경 변수를 그대로 읽는다(로컬에서 확인).

## 6. 통신 정책

foundation의 `default-deny`(Ingress·Egress)와 DNS 허용 위에 다음만 연다.

- data: `allow-api-to-postgres`(TCP 5432), `allow-api-to-redis`(TCP 6379). 출발지는 namespace `nerdnam` 안의 `app: api` Pod만.
- nerdnam: `allow-api-to-data` — `app: api` Pod에서 data namespace의 `app: postgres`:5432, `app: redis`:6379로 나가는 것만.
- AI·FE·Traefik은 DB·Redis에 접근할 수 없다. 7단계 exporter·Prometheus 경로는 그때 추가한다.
- probe는 exec 방식이라 kubelet → Pod 네트워크 허용이 필요 없다.

## 7. 보존·삭제 보호

보호 계층은 서로 독립이다.

1. StatefulSet `persistentVolumeClaimRetentionPolicy`: 삭제·축소 모두 `Retain`.
2. StorageClass `gp3-retain`: PV `reclaimPolicy: Retain` (PVC를 지워도 EBS는 남는다).
3. Argo: StatefulSet에 `Prune=false,Delete=false`, 자동 sync 없음. PVC는 StatefulSet 컨트롤러가 만들어 Argo가 추적·prune하지 않는다.

## 8. 배포·업데이트 절차 (사용자가 실행)

동기화 순서(수동 sync): `nerdnam-foundation` → `nerdnam-secrets`(ExternalSecret `SecretSynced` 확인) → `nerdnam-data`. Secret이 없으면 Pod는 `CreateContainerConfigError`로 기다린다.

- **이미지 업데이트**: digest를 바꾸고 sync하면 replica 1이라 Pod가 내려갔다 올라온다(중단). 점검 창에서 한다. PostgreSQL 메이저 버전(17 → 18)은 데이터 디렉터리 형식이 바뀌어 이미지 교체만으로 안 된다(dump/restore 또는 pg_upgrade, 백업 단계 이후).
- **pgvector 업데이트**: 이미지 교체 뒤 슈퍼유저로 `ALTER EXTENSION vector UPDATE;`. migrator·app은 권한이 없다.
- **PVC 용량 증설**: `volumeClaimTemplates`는 StatefulSet에서 바꿀 수 없다. PVC `data-postgres-0`을 직접 늘리고(`allowVolumeExpansion`), Git 값은 기록용으로 맞춘 뒤 StatefulSet을 `--cascade=orphan`으로 지우고 다시 sync한다.
- **설정 변경**: ConfigMap 내용이 바뀌면 Pod template checksum이 바뀌어 재시작된다. 초기화 스크립트 변경은 기존 DB에 적용되지 않는다(운영 SQL로 따로 적용).
- **노드 drain**: PDB를 두지 않았다. drain하면 DB·Redis가 중단되고 같은 AZ(private-c)의 새 노드에서 EBS가 다시 붙는다. 점검 창에서만 한다.
- 백업이 생기기 전에는 데이터가 있는 PVC 삭제·파괴적 schema 변경을 하지 않는다.

## 9. 검증 결과

로컬 검증(2026-10-28):

- `scripts/validate_gitops.py`: 자체 chart 6개 lint/render, 공식 chart 5개, CR 16개 CRD schema, 기존 배치 검사 15개 통과. 데이터 계층 검사 추가: 배치·toleration, PVC StorageClass·RWO·Retain, digest 고정, Pod 보안, probe, CPU limit 없음, Secret 키 계약, BE 매핑(슈퍼유저 키 제외), quota 합계, 양쪽 NetworkPolicy 일치. 각 검사를 일부러 깨뜨려 실패하는 것도 확인했다.
- 로컬 Docker(Pod와 같은 uid·gid, 읽기 전용 root, capability 제거, `lost+found`가 있는 root 소유 볼륨, 0444 ConfigMap 파일)로 렌더된 설정을 실행:

  - app 계정: DML 가능, 테이블 생성·삭제·스키마 생성·확장 변경 거부. 틀린 비밀번호 거부, migrator의 `postgres` DB 접속 거부.
