# 부하 시험 (동시 요청 수·요청량 변화 → 성능 지표·자원 사용량)

기준일: 2026-11-02. 상태: **코드·로컬 검증 완료. 클러스터에서 실제로 돌린 결과는 아직 없다(배포 후).**

## 1. 방식

노트북에서 k6 스크립트를 돌리던 방식(`scripts/load/read-only.js`)을 **클러스터 안 k6-operator + Prometheus + Grafana** 방식으로 바꿨다.

```text
kubectl create -f gitops/load/testruns/<시나리오>.yaml
        │
        ▼
k6-operator (k6-operator ns, platform 노드)
        │  initializer → runner → starter Pod 를 load-test ns 에 띄운다
        ▼
k6 runner ──HTTPS──▶ 서비스 도메인 (NLB → Traefik → web·api)   ← 실제 사용자와 같은 경로
   │
   └─ remote write ─▶ Prometheus (/api/v1/write) ◀── 기존 수집: BE·cAdvisor·kube-state-metrics·exporter
                                │
                                ▼
                     Grafana "nerdnam 부하 시험" 대시보드
                     (k6 가 보낸 부하 ↔ 서버 응답 ↔ 자원 사용량을 같은 시간축에)
```

노트북 방식보다 나은 점:

| | 노트북에서 k6 | 클러스터 안 k6-operator |
| --- | --- | --- |
| 결과 보기 | 터미널 요약만. 서버 지표는 Grafana 에서 따로 시간을 맞춰 봐야 한다 | k6 지표가 Prometheus 로 들어가 서버 지표와 **한 대시보드·한 시간축** |
| 재현성 | 실행한 사람의 PC·회선·명령어 옵션에 따라 다르다 | 시나리오가 Git 의 TestRun YAML 로 고정. 누가 돌려도 같다 |
| 부하 발생기 한계 | 집·카페 회선이 먼저 막힐 수 있다 | AWS 안에서 보낸다. k6 Pod 의 CPU 도 대시보드에서 본다 |
| 지난 시험과 비교 | 터미널 출력을 따로 저장해야 한다 | `testid` 로 골라 Prometheus 보존 기간(7일) 동안 다시 본다 |

노트북에서 직접 돌리는 것도 그대로 된다(스크립트 상단 주석). 이때 결과는 터미널에만 나온다.

## 2. 구성

| 파일 | 내용 |
| --- | --- |
| `gitops/root/values.yaml`, `configs/k6-operator.yaml` | k6-operator chart 4.7.0(앱 1.7.0, `charts.lock.json` 에 SHA256). platform 노드, requests 20m/64Mi |
| `gitops/root/configs/kube-prometheus-stack.yaml` | Prometheus `enableRemoteWriteReceiver: true`(ClusterIP 라 클러스터 안에서만), kube-state-metrics `metricLabelsAllowlist: nodes=[workload]`(노드 역할 라벨) |
| `gitops/load` (Argo `nerdnam-load`) | `k6-scripts` ConfigMap(`scripts/*.js`), `k6-env` ConfigMap(대상 도메인 `https://<appHostname>`, Prometheus 쓰기 주소, 응답 시간 통계 avg·max·p95·p99), `load-test` ResourceQuota |
| `gitops/load/testruns/{smoke,concurrency,rate}.yaml` | TestRun. **Argo 가 띄우지 않는다**(sync 마다 시험이 돌면 안 된다). 운영자가 `kubectl create` |
| `gitops/observability/dashboards/nerdnam-load.json` | Grafana "nerdnam 부하 시험" |
| `gitops/foundation`, `gitops/seed` | `load-test` namespace, AppProject 대상에 `k6-operator`·`load-test` 추가 |

- k6 Pod(runner 500m/512Mi, limit 1Gi)는 **platform 노드**에 뜬다. app 노드에 띄우면 부하 발생기가 측정 대상과 CPU 를 나눠 써서 결과가 흐려진다. 용량 검사에 시험 중 Pod(runner + starter)를 더해도 platform 노드 CPU requests 1.85 / 3.92 이다.
- `load-test` namespace quota: requests CPU 1.5, 메모리 2Gi, limit 3Gi, Pod 6개. 시험 하나가 이 안에 들어간다(검증 스크립트가 계산).
- 이미지 digest 고정: `grafana/k6:1.3.0`, `ghcr.io/grafana/k6-operator:starter-v1.7.0`.
- 부하는 클러스터 안 → NAT Gateway → NLB(공인) → Traefik 으로 돌아 들어온다. 실제 사용자 경로와 같지만 NAT 처리 요금(GB 당)이 붙는다. 읽기 경로 응답은 작아서 17분 시험에 수백 MB 수준으로 예상한다(실측 후 기록).

## 3. 시나리오

모두 **읽기 경로만** 부른다(AI 분석·가이드 생성은 Bedrock 요금 때문에 부르지 않는다). 반복 1번 = `/`(web) + `/api/auth/csrf` + `/api/projects`(비로그인 401). 시험 계정 쿠키를 주면 `/api/me` 등 로그인 경로 6개.

| TestRun | 무엇을 바꾸나 | 기본 단계 | 시간 |
| --- | --- | --- | --- |
| `smoke` | 고정 초당 2회 | `RATE=2`, `DURATION=2m` | 2분 |
| `concurrency` | **동시 사용자 수**(VU). 각 VU 는 한 바퀴 돌고 1초 쉰다. 서버가 느려지면 요청량도 줄어든다 | VU 10 → 20 → 40 → 80, 1분 올리고 3분 유지 | 약 17분 |
| `rate` | **초당 요청량**. 서버가 느려져도 k6 가 VU 를 늘려 요청량을 유지한다(최대 `MAX_VUS=300`) | 초당 반복 2 → 5 → 10 → 20 | 약 17분 |

- 단계는 TestRun 의 `STAGES` 값(`목표:시간` 쉼표 목록)을 바꿔서 조절한다. runner 와 initializer 가 같은 env 를 보도록 YAML anchor(`&env`/`*env`)로 묶었다.
- 두 시험을 함께 보는 이유: `concurrency` 는 "사용자가 N명 동시에 쓰면?"(닫힌 모델), `rate` 는 "초당 N건이 들어오면?"(열린 모델)이다. 서버가 느려질 때 `concurrency` 는 요청량이 저절로 줄어 한도가 가려지고, `rate` 는 대기열이 쌓여 응답 시간이 급격히 는다.
- 첫 측정은 `smoke` → `rate` → `concurrency` 순서. 한도가 보이면(아래 4절) 그 아래에서 단계를 잘게 나눠 다시 돈다.

## 4. 대시보드 "nerdnam 부하 시험"

상단 `시험` 변수로 `testid`(기본 `<시작 시각 UTC>-<시나리오>`, 최신이 위)를 고른다. 시간 범위는 시험 시작~끝으로 맞춘다.

| 행 | 패널 | 읽는 법 |
| --- | --- | --- |
| 부하 (k6) | 동시 사용자(VU), 보낸 요청/초·못 보낸 반복, k6 p95(web·api), 실패 비율, 상태 코드별 요청/초, k6 Pod CPU | "못 보낸 반복"이 생기거나 k6 Pod CPU 가 requests 에 붙으면 **부하 발생기가 한계**다. 그 구간은 서버 한도가 아니다 |
| 서버 응답 (BE) | BE 요청/초(상태별), BE p95(전체·경로별), DB 연결 풀 | k6 p95 − BE p95 ≈ NLB·Traefik·네트워크 몫. DB 연결 "대기" > 0 이면 연결 풀이 병목 |
| 자원 사용량 | 노드 CPU·메모리 사용률(역할별), Pod CPU(코어·requests 대비), Pod 메모리 / limit, JVM heap, PostgreSQL 활성 연결·커밋/초, Redis 명령/초·연결 | 단계마다 같이 오르는지, 어느 것이 먼저 포화되는지 |

한도 판단(측정 전 시작값. 첫 실측 후 조정): k6 API p95 > 800ms 또는 web p95 > 1.5s, 실패 비율 > 1%, app 노드 CPU > 80%, Pod 메모리 / limit > 90%, DB 연결 대기 > 0 중 하나가 **유지 구간 3분 내내** 나타나면 그 단계를 한도로 본다.

참고: BE 지표 수집 간격은 30초라 BE 패널은 k6 패널보다 늦게 따라온다. cAdvisor(Pod CPU·메모리)는 10초, k6 는 5초마다 들어온다.

## 5. 절차 (배포 후)

```bash
# 0. Grafana 열기: https://grafana.<도메인> (관리 IP 에서만). 안 되면 kubectl -n monitoring port-forward svc/grafana 3000:80

# 1. operator·스크립트 확인
kubectl -n k6-operator get deploy
kubectl -n load-test get configmap k6-scripts k6-env

# 2. (선택) 로그인 경로까지: 시험용 계정 SESSION 쿠키. 저장소·채팅에 남기지 않는다. 끝나면 지운다
kubectl -n load-test create secret generic k6-session --from-literal=SESSION=<쿠키 값>

# 3. 시험 시작 → 진행 확인
kubectl create -f gitops/load/testruns/smoke.yaml
kubectl -n load-test get testrun           # STAGE: initialization → created → started → finished
kubectl -n load-test logs -f -l runner=true

# 4. 끝나면 TestRun 을 지운다(Pod 도 함께). 지표는 Prometheus 에 남는다
kubectl -n load-test delete testrun <이름>
kubectl -n load-test delete secret k6-session
```

- 한 번에 시험 하나만 돌린다(quota 도 하나만 들어가게 잡았다).
- 시험이 서비스를 실제로 느리게 만들 수 있다. 사용자가 쓰는 시간을 피하고, 이상하면 `kubectl -n load-test delete testrun --all` 로 바로 멈춘다.
- 노드를 내린 상태(`docs/운영-중지-재개.md`)에서는 돌리지 않는다.
