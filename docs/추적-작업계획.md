# 8단계 분산 추적 (OpenTelemetry·Tempo)

기준일: 2026-10-29. 상태: **INFRA 코드·로컬 검증 완료, 미배포. 앱 계측은 앱 저장소 이슈로 진행 중.** "확인함"은 로컬 Helm 렌더링·Terraform mock 테스트·로컬 Docker 실행 결과다. 실제 BE→AI→Bedrock trace, Pod Identity로 S3 쓰기, NetworkPolicy 허용은 배포 후 검증할 항목이다.

범위 밖: 브라우저 RUM, tail sampling(오류 trace 100% 보존), Tempo metrics-generator(service graph·span 지표), CloudWatch 연계.

## 1. 경로

```text
web·api·ai ── OTLP HTTP 4318 ──> Alloy (monitoring, 7단계와 같은 Pod) ── OTLP gRPC 4317 ──> Tempo ──> S3 (nerdnam-dev-tempo-<계정>-ap-northeast-2)
Grafana ──> Tempo 데이터 소스 ⇄ Loki (trace_id 로 서로 이동)
```

- 앱은 Tempo로 직접 보내지 않는다. Alloy가 받는 곳을 하나로 모으고, 메모리 상한(`memory_limiter` 256MiB)을 넘으면 새 span을 거절한다. 그래서 trace가 몰려도 Alloy가 OOM으로 로그 수집까지 멈추지 않는다.
- OTLP로는 **trace만** 받는다. 지표는 Prometheus, 로그는 stdout → Loki가 맡는다(구축 계획 6장 "수집 중복"). 앱 환경 변수도 `OTEL_METRICS_EXPORTER=none`, `OTEL_LOGS_EXPORTER=none`.
- 구축 계획은 "노드별 Alloy receiver"였지만, 7단계에서 Alloy를 platform 노드의 Deployment 1개로 바꿨으므로 Service `alloy.monitoring.svc.cluster.local:4318` 하나로 받는다.

| 구성요소 | 차트(고정 버전) | 저장 | 자원(requests / limit) |
| --- | --- | --- | --- |
| Tempo | grafana-community/tempo `3.2.0` (Tempo 3.1.0), monolithic 1개, platform 노드 | trace block **S3**, WAL·live-store gp3-retain 10Gi, 보존 3일 | 100m / 512Mi, 1.5Gi |
| Alloy | 7단계와 같음 | — | 7단계와 같음 |

- grafana 저장소의 `tempo` 차트는 2026-01에 지원 중단(deprecated)되어 grafana-community 저장소로 옮겨졌다. 2주 이상 된 마지막 버전 3.2.0을 SHA256으로 고정하고 AppProject `sourceRepos`에 저장소를 추가했다.
- Tempo 3.x의 microservices 모드는 Kafka가 필요하지만 **monolithic은 필요 없다**(로컬 실행으로 확인). 공식 문서는 monolithic을 본격 운영용으로 권하지 않는다. 규모가 커지면 관리형 tracing이나 분산 모드를 검토한다.
- **설정 파일을 직접 쓴다.** 차트의 Service 템플릿이 `tempo.receivers.jaeger`를 필수로 읽어 values로는 Jaeger 수신을 끌 수 없다. 그래서 `config`를 직접 써서 OTLP gRPC 4317만 듣게 했다. 차트 Service에는 고정된 jaeger·zipkin 포트 이름이 남지만 Tempo가 그 포트를 듣지 않는다.
- 비root(uid 10001), 읽기 전용 root, capability 전부 제거. 쓰기는 PVC(`/var/tempo`)와 `/tmp` emptyDir만 한다.
- 공개하지 않는다(ClusterIP, Ingress 없음). Grafana에서만 조회한다.

## 2. 앱 계약 (INFRA가 넣는 환경 변수)

`gitops/apps/templates/_helpers.tpl`의 `apps.otelEnv`가 web·api·ai에 같은 형식으로 넣는다. 계측이 없는 지금 이미지에는 영향이 없다.

| 변수 | 값 |
| --- | --- |
| `OTEL_SERVICE_NAME` | `web` / `api` / `ai` — Pod `app` 라벨 = Loki `app` 라벨 |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://alloy.monitoring.svc.cluster.local:4318` |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` |
| `OTEL_TRACES_EXPORTER` / `OTEL_METRICS_EXPORTER` / `OTEL_LOGS_EXPORTER` | `otlp` / `none` / `none` |
| `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG` | `parentbased_traceidratio` / `1.0` (`values.yaml` `tracing.sampleRatio`) |
| `OTEL_RESOURCE_ATTRIBUTES` | `k8s.cluster.name`, `k8s.namespace.name`, `k8s.pod.name`(downward API `K8S_POD_NAME`) |

- 샘플링: 구축 계획 7장대로 개발 검증 동안 100%, 수집량을 잰 뒤 10%로 내린다. parent-based라서 BE가 정한 샘플링을 AI가 따른다. head sampling이라 오류 trace가 모두 남는다고 보장하지 않는다.
- 통신 정책: web·api·ai 각 egress에 `monitoring` namespace의 `app.kubernetes.io/name=alloy` Pod, TCP 4318만 추가했다. monitoring namespace는 아직 default-deny가 아니라 Alloy ingress는 따로 열 필요가 없다.

## 3. 로그 ↔ trace 연결 (Grafana)

- Tempo 데이터 소스(uid `tempo`): trace → 로그는 `service.name` → Loki `app` 라벨, 같은 trace_id, span 시간 ±5분으로 찾는다.
- Loki 데이터 소스: 로그 줄의 `trace_id`(또는 `traceId`)에서 32자리 소문자 16진수를 찾아 Tempo로 연결한다. JSON(`"trace_id":"…"`)과 `trace_id=…` 둘 다 읽는다. `member_id` 같은 다른 32자리 값은 잡지 않는다(검증 스크립트가 확인).
- Grafana는 provisioning 파일의 `${…}`를 환경 변수로 바꾼다. 그래서 링크 질의는 `$${__value.raw}`로 쓴다(`$` 하나면 빈 값이 된다).
- 지금 세 앱 모두 JSON 로그·trace_id가 없다. 앱 이슈에서 같은 형식을 요청했다.

## 4. AWS 자원 (Terraform `modules/observability`)

- 7단계 Loki 구성을 `for_each`로 일반화해 Loki·Tempo가 **bucket과 역할을 따로** 갖는다. 같은 규칙이 둘 다에 적용된다: 공개 차단, BucketOwnerEnforced, SSE-S3, TLS 아닌 요청 거부, 미완료 multipart 1일 정리, lifecycle = 보존 일수 × 4(Tempo 12일, Loki 28일).
- 역할 `nerdnam-dev-tempo`: Pod Identity로 `monitoring/tempo`에만 연결. 그 bucket의 List·Get·Put·Delete만.
- 리소스 주소가 `aws_s3_bucket.loki` → `aws_s3_bucket.store["loki"]`로 바뀌었다. 아직 apply한 적이 없어 옮길 state가 없다. **apply한 뒤에 같은 변경을 하면 `moved` 블록이 필요하다.**
- Tempo 3.1.0의 S3 클라이언트(minio-go v7.2.0)는 EKS Pod Identity(`AWS_CONTAINER_CREDENTIALS_FULL_URI` + 토큰 파일)를 지원한다(소스 확인). 정적 키를 넣지 않는다.
- bootstrap이 `environment.tempoBucket`을 넘긴다. 실행자 IAM 초안 `NerdnamTerraformObservabilityDev`에 Tempo bucket·역할을 추가했다.

## 5. 배포 순서 (사용자가 실행)

1. AWS 루트 apply(Tempo bucket·역할·association) → bootstrap apply(seed 갱신: 새 sourceRepo, tempoBucket).
2. 수동 sync: tempo → alloy(OTLP 수신) → kube-prometheus-stack(Grafana 데이터 소스) → apps(환경 변수·egress).
3. 확인: Tempo `/ready`, Prometheus target(tempo) up, S3에 block 생성, Grafana Explore에서 Tempo 검색. 앱 계측이 들어온 뒤 BE→AI→Bedrock trace와 로그 이동.

## 7. 검증 결과

로컬(2026-10-29):

- `scripts/validate_gitops.py`: 공식 chart 9개(Tempo 추가, SHA256 확인), CR 28개, 기본 객체 52개 1.35 엄격 검사, upstream 배치 23개. 추적 검사:
  - 앱마다 `OTEL_*` 계약, `K8S_POD_NAME`이 `OTEL_RESOURCE_ATTRIBUTES`보다 앞(치환 순서)
  - 앱 egress → Alloy Pod 라벨·포트가 실제 Alloy Deployment·Service와 맞음
  - Alloy는 HTTP만 받고 Tempo 4317로 보냄, memory_limiter 있음, OTLP 지표·로그 없음
  - Tempo: StatefulSet 1개, SA `tempo`, platform, gp3-retain, 읽기 전용 root, S3 bucket 이름, 정적 키·`insecure` 없음, WAL은 PVC, 수신은 OTLP gRPC만, 보존 72h, 사용 통계 끔
  - Grafana Tempo·Loki 데이터 소스 uid 상호 참조, `$$` 이스케이프, trace_id 정규식(JSON·key=value·traceId 일치, member_id 불일치)
- 일부러 틀리게 바꾼 4곳이 모두 걸러졌다: AI의 Alloy egress 삭제, Tempo 정적 키, Alloy→Tempo 포트 오류, Grafana `$` 이스케이프 누락.
- Terraform mock 테스트 14개(observability: 두 bucket 이름·공개 차단·lifecycle > 보존·association 대상·각자 자기 bucket만·역할 이름), bootstrap 1개(tempoBucket 전달).
- 로컬 Docker(렌더된 설정 그대로, Pod와 같은 uid·읽기 전용 root·capability 제거, 클러스터 DNS 이름을 network alias로):
  - OTLP HTTP span → Alloy 4318 `200` → Tempo 조회 `200`(같은 trace).
  - S3 대신 SeaweedFS(S3 호환)를 쓰려고 endpoint·`insecure`·정적 키·짧은 flush 시간만 시험용으로 바꿨다. Tempo가 bucket에 `data.parquet`·`index`·`bloom`·`meta.json`을 썼고, flush 뒤에도 같은 trace를 조회했다.
  - Tempo는 시작할 때 bucket에 닿지 않으면 바로 종료한다(실제로 확인). 배포 때 Pod Identity·bucket 문제는 CrashLoop로 바로 드러난다.
  - 메모리: Tempo 약 150MiB, Alloy 약 50MiB(span 몇 개 기준. 실제 부하 측정 아님).

배포 후 검증할 것: Pod Identity로 S3 쓰기, 3일 뒤 block 삭제, NetworkPolicy(앱 → Alloy 허용, 그 밖 차단), 앱 계측 후 BE→AI→Bedrock trace 연결과 비동기 작업 link, Grafana 로그 ↔ trace 이동, 100% 샘플링에서 수집량·Alloy·Tempo 메모리.
