# 6단계 앱 배포 (FE·BE·AI)

기준일: 2026-10-28. 상태: **INFRA 쪽 코드·로컬 검증 완료, 미배포.** 이 문서의 "확인함"은 로컬 Helm 렌더링·Terraform mock 테스트·로컬 Docker 실행 결과다. EKS 위 실행, Pod Identity 자격 증명, 실제 Bedrock 호출, OAuth 로그인, NetworkPolicy 차단은 배포 후 검증할 항목이다.

기준 앱 커밋: FE `9cabb09`, BE `3fe36e0`, AI `9854173`(모두 `origin/main`, 2026-10-29 이슈 반영 후 재검토). SPEC v1.64.

범위 밖: 앱 저장소 코드·workflow 변경(아래 7절에 할 일로 정리), 관측(7·8단계), S3 백업.

## 1. 구성

| | web (FE) | api (BE) | ai (AI) |
| --- | --- | --- | --- |
| 이미지 | ECR `nerdnam-dev/web` digest | ECR `nerdnam-dev/api` digest | ECR `nerdnam-dev/ai` digest |
| 포트 / Service | 3000 / `web` | 8080 / `api` (+ 관리 8081 `management`) | 8000 / `ai` |
| 실행 사용자 | uid 100 / gid 101 (이미지의 `web`) | 10001 (이미지의 `nerdnam`) | 65532 (이미지 `USER 65532`, AI #34) |
| 자원 | 100m / 256Mi, limit 512Mi | 500m / 1.5Gi, limit 2Gi (`MaxRAMPercentage=75`) | 250m / 512Mi, limit 1Gi |
| 교체 | RollingUpdate (surge 1) | **Recreate** | RollingUpdate (surge 1) |
| 종료 유예 | 30초 + preStop 5초 | 90초 | 330초 + preStop 5초 |
| readiness | `GET /healthz` (FE #11, 2026-10-30. 전에는 `/favicon.ico`) | `GET :8081/actuator/health/readiness` (readinessState·db·redis) | `GET /readyz` |
| liveness | `GET /healthz` (전에는 TCP 3000) | `GET :8081/actuator/health/liveness` (startup 최대 5분, Flyway) | `GET /livez` |

- 모두 app 노드(`workload=app`), replica 1, 읽기 전용 root, capability 제거, ServiceAccount token 자동 마운트 없음. 쓰기 경로는 emptyDir(`/tmp`, FE `/app/.next/cache`).
- **BE 관리 포트**: `MANAGEMENT_PORT=8081`이면 actuator(probe·`/actuator/prometheus`·`/actuator/aijob`)가 8081에만 있고 공개 포트 8080에는 없다(BE #42·#44, 로컬에서 8080의 actuator 404/401 확인). 8081은 Ingress·web에서 닿지 않는다(NetworkPolicy). 7단계 Prometheus만 열 예정이다.
- **BE Recreate**: 앱 시작 Flyway와 메모리 작업 큐 때문에 두 버전이 동시에 뜨지 않게 한다. 교체 중에는 API가 중단된다.
- **AI probe**: `/livez`는 프로세스, `/readyz`는 첫 연결 확인이 끝나고 LLM·임베딩 중 하나라도 쓸 수 있을 때 200(AI #35). 저장된 상태만 읽고 Bedrock을 부르지 않는다. 둘 다 `error`면 Service에서 빠져 BE가 연결 실패 → `GPU_UNAVAILABLE`로 처리한다. 이미지의 uvicorn은 종료 신호 뒤 최대 300초 기다린다(AI #34) — 종료 유예 330초 안.

## 2. 공개 경로와 HTTPS

```text
인터넷 → NLB(TCP 443) → Traefik(TLS 종료, 인증서 nerdnam-web-tls)
  /api, /oauth2, /login/oauth2  → api:8080
  그 밖 전부                     → web:3000  (web 은 SSR·rewrites 로 api 를 다시 부른다)
```

- 80 → 443 리다이렉트는 Traefik 설정(4단계)에 있다. `/actuator`·AI는 공개 경로에 없다(web 쪽 404 확인).
- 인증서: `Certificate nerdnam-web`(DNS01, `nerdnam-acme`). 도메인은 bootstrap 입력 `app_hostname` → `environment.appHostname`.
- BE는 `SERVER_FORWARD_HEADERS_STRATEGY=native`로 Traefik의 `X-Forwarded-*`를 믿는다(Tomcat 기본 내부 프록시 대역 10.x 포함). 로컬에서 OAuth 시작 응답의 `redirect_uri`가 `https://<도메인>/login/oauth2/code/google`, 세션 쿠키가 `Secure; HttpOnly; SameSite=Lax`인 것을 확인했다.
- **OAuth 콘솔 등록**: Google·Kakao에 `https://<app_hostname>/login/oauth2/code/google`, `…/kakao`를 redirect URI로 등록한다.
- 웹 도메인의 DNS 레코드(NLB 주소를 가리키는 A alias/CNAME)는 아직 자동 생성하지 않는다. 배포 후 수동으로 만든다(4단계와 같음).

| 환경 변수 | 값 |
| --- | --- |
| `NERDNAM_AUTH_MODE` | `session` |
| `NERDNAM_AUTH_WEB_ORIGIN` | `https://<app_hostname>` |

- AI: `AI_MODE=real`, `AWS_REGION`, `LLM_MODEL=global.amazon.nova-2-lite-v1:0`, `EMBED_MODEL_ID=amazon.titan-embed-text-v2:0`, `AWS_EC2_METADATA_DISABLED=true`(노드 역할로 넘어가지 않게). `AWS_BEARER_TOKEN_BEDROCK`·정적 키는 넣지 않는다. `nerdnam/dev/ai` Secret은 지금 쓰지 않는다(Pod에 연결하지 않음).

## 4. AI의 Bedrock 권한 (Terraform `modules/workload`)

- 역할 `nerdnam-dev-ai`, EKS Pod Identity로 `nerdnam/ai` ServiceAccount에만 연결. trust는 클러스터 ARN·namespace·SA 태그 조건.
- 권한은 `bedrock:InvokeModel` 하나(Converse도 이 권한). AI 코드가 `converse`·`invoke_model`만 쓰는 것을 확인했다.
  - Titan 임베딩: `arn:aws:bedrock:ap-northeast-2::foundation-model/amazon.titan-embed-text-v2:0`, 요청 리전 서울.
  - Nova 2 Lite Global 프로필: AWS 문서의 3단 구성 — 서울 inference-profile, 서울 foundation-model(`bedrock:InferenceProfileArn` 조건), 리전 없는 global foundation-model(`aws:RequestedRegion=unspecified` + 프로필 조건).
- boto3/botocore 1.43.119는 Pod Identity 자격 증명을 지원한다. AI Pod egress는 Pod Identity Agent `169.254.170.23:80`과 외부 443만 연다.
- 조직 SCP가 리전을 막고 있다면 `unspecified` 허용이 필요하다(문서 기준, 이 계정의 SCP는 확인하지 않음).

## 5. 이미지 CI와 배포 흐름

```text
앱 저장소 main merge → 테스트 → 이미지 빌드 → GitHub OIDC 로 nerdnam-dev-ci-<web|api|ai> 역할 → ECR push
  → 실행 요약(Actions summary)에 digest 출력 → 운영자가 INFRA gitops/apps/images.yaml 을 고치는 PR → merge → Argo 수동 sync → 확인
```

- **팀 결정(2026-10-29, FE `2fab009`)**: 앱 CI는 ECR에 올리기까지만 한다. INFRA 저장소는 앱 CI가 고치지 않고, 운영자가 실행 요약의 digest를 보고 `images.yaml` PR을 만든다. 앱 저장소에 INFRA 쓰기 권한(GitHub App·토큰)을 주지 않는다.
- Terraform `modules/workload`가 GitHub OIDC provider와 CI 역할 3개를 만든다. 각 역할은 **해당 저장소의 `main` 브랜치 workflow만** 받을 수 있고(`sub = repo:nerd-nam/<repo>:ref:refs/heads/main`), **자기 ECR repository에만** push한다. 저장소 이름·브랜치는 변수(`github_repositories`, `ci_branch`)다.
- 계정에 같은 URL(`token.actions.githubusercontent.com`)의 OIDC provider가 이미 있으면 생성이 실패한다. 그때는 `terraform import module.workload.aws_iam_openid_connect_provider.github <ARN>`으로 가져온다. 2026-10-29 확인 결과 이미 있어서(클라이언트 `sts.amazonaws.com`, 코드와 같음) import했다. 철거 때 주의는 runbook 7절.
- 이미지 digest는 Terraform·bootstrap이 아니라 Git의 `gitops/apps/images.yaml`이 소유한다(root Application이 `valueFiles: [images.yaml]`로 읽음). 지금은 비어 있어 렌더링이 실패한다 — 첫 이미지 push 전에는 `nerdnam-apps`를 sync하지 않는다. 가짜 digest를 넣지 않는다.
- ECR은 IMMUTABLE 태그다. 세 workflow 모두 commit SHA를 태그로 쓴다. 배포 정의는 태그가 아니라 digest로 고정한다.

앱 저장소 workflow (2026-10-29 확인, 모두 `main` push에서만 ECR 단계 실행, 저장소 변수가 비면 건너뜀):

| 저장소 | 파일 | 역할 ARN 저장소 변수 (값: `terraform output workload`) | 비고 |
| --- | --- | --- | --- |
| FE | `.github/workflows/image.yaml` | `AWS_ROLE_ARN` ← `ci_role_arns.web` | lint·build 후 push. `API_ORIGIN`을 **빌드 값**으로 넣는다(Next.js rewrites가 빌드 때 고정) |
| BE | `.github/workflows/push-image.yml` | `AWS_CI_ROLE_ARN_API` ← `ci_role_arns.api` | |
| AI | `.github/workflows/ci.yml` | `AWS_CI_ROLE_ARN` ← `ci_role_arns.ai` | 테스트 후 push |

- FE 이미지에 빌드 때 들어간 `API_ORIGIN`(`http://api.nerdnam.svc.cluster.local:8080`)과 INFRA web Deployment의 `API_ORIGIN` 환경 변수는 같아야 한다. BE Service 이름·포트를 바꾸면 FE 이미지를 다시 빌드해야 한다.

## 6. 통신 정책 (nerdnam namespace)

foundation의 default-deny와 DNS 허용, 5단계 `allow-api-to-data` 위에:

| 출발 → 도착 | 포트 |
| --- | --- |
| traefik namespace → web | 3000 |
| traefik namespace, web → api | 8080 |
| api → ai | 8000 |
| api → 외부(사설 대역 제외 0.0.0.0/0) | 443 (Google·Kakao OAuth) |
| ai → 외부(사설 대역 제외) | 443 (Bedrock) |
| ai → Pod Identity Agent `169.254.170.23/32` | 80 |

- web은 api 말고는 나갈 곳이 없다. web·ai는 DB·Redis에 닿지 않는다. IMDS(169.254.169.254)는 모두 막힌다.
- 외부 443을 도메인 단위로 좁히지는 못한다(NetworkPolicy는 IP 기준). 더 좁히려면 egress proxy가 필요하다.
- 7단계에서 Prometheus 수집·OTLP 전송 경로를 추가한다.
- nerdnam namespace에 ResourceQuota(LoadBalancer·NodePort·PVC 0개, rolling update 여유 포함)와 LimitRange를 둔다.

검토에서 남은 점 (INFRA가 바꿀 수 없는 앱 쪽 결정, 각각 [BE#50](https://github.com/nerd-nam/BE-nerdnam/issues/50)·[SPEC#91](https://github.com/nerd-nam/SPEC-nerdnam/issues/91)로 발행):

1. **(해결, [BE#50](https://github.com/nerd-nam/BE-nerdnam/issues/50) → BE #52)** **drain 하면 BE 전체가 Service에서 빠진다.** drain은 readiness를 `REFUSING_TRAFFIC`으로 바꾸고(BE 문서에 의도로 적혀 있음), BE는 replica 1이다. 그래서 drain을 건 순간부터 교체가 끝날 때까지 AI 작업뿐 아니라 로그인·조회 등 **모든 API가 503**이다. 진행 중 작업이 끝나기를 기다리는 시간(최악 약 11분)만큼 전면 중단이 길어진다. 새 AI 작업만 거절하고 readiness는 유지하면 그동안 다른 API는 계속 쓸 수 있다. → BE #52에서 drain은 새 AI 작업만 503 `AI_UNAVAILABLE`로 거절하고 readiness는 그대로 둔다. SIGTERM 뒤 정리는 Spring graceful shutdown(단계당 30초, 종료 유예 90초 안)이 맡는다.
2. **(열림, [SPEC#91](https://github.com/nerd-nam/SPEC-nerdnam/issues/91))** **AI 시간 상한이 BE 설정과 어긋난다.** AI는 `/embed` 예산 8초("BE 읽기 제한 10초 안"), LLM 대기 5초("가장 짧은 읽기 제한 20초 안")를 SPEC 계약(C-04: `/embed` 10초·`/extract` 20초…)에 맞췄다. 그런데 BE는 실측(호출 한도에 걸린 32건 배치 19~34초)으로 읽기 제한을 120~300초로 늘렸고 계약은 그대로다. 한도에 걸리는 상황에서는 AI가 8초 만에 503 → BE가 1회 재시도 후 `GPU_UNAVAILABLE`로 끝낸다. 세 저장소가 같은 시간표를 보도록 SPEC 계약 갱신이 필요하다. AI 값은 환경 변수(`EMBED_BUDGET`, `LLM_QUEUE_WAIT` 등)라 합의되면 INFRA에서 넣을 수 있지만, 임의로 바꾸지 않았다.

로컬 확인(`origin/main` 이미지, Pod와 같은 보안 조건): BE 8081의 `health/liveness`·`readiness`·`prometheus`·`aijob` 200, 8080의 actuator 404/401, 지표 7개 출력, drain 중 readiness 503·liveness 200, resume 후 200, Pod 안 `curl`로 `aijob` 접근. AI 이미지 기본 uid 65532, `/livez` 200, 자격 증명 없이 `/readyz` 503.

8단계 추가(2026-10-29): 세 앱에 표준 `OTEL_*` 환경 변수와 각 앱 → `monitoring/alloy:4318` egress를 넣었다(추적 문서 2절). 계측 요청은 BE#51·AI#42·FE#10. 위 7절 표의 AI uid 주석도 AI #34 반영(이미지 `USER 65532`)으로 고쳤다.

## 8. 배포 순서와 운영 (사용자가 실행)

1. AWS 루트 apply(`modules/workload` 포함) → bootstrap apply(`app_hostname` 입력).
2. Secrets Manager `nerdnam/dev/backend`에 OAuth 키 4개, `nerdnam/dev/data`에 5단계 키 4개 공급.
3. 앱 저장소 CI가 ECR에 이미지 push → 운영자가 실행 요약의 digest로 `images.yaml` PR → merge.
4. 수동 sync: foundation → secrets → data(Ready 확인) → apps. BE 첫 기동 때 Flyway가 V1~V8을 적용한다.
5. NLB 주소로 웹 도메인 DNS 레코드 생성 → 인증서 발급 확인 → OAuth 콘솔 redirect URI 등록 → 로그인 확인.

- BE 배포 전 작업 비우기(BE #45). 관리 포트는 Pod 안에서만 닿으므로 `kubectl exec`를 쓴다:

  ```sh
  kubectl -n nerdnam exec deploy/api -- curl -s -X POST localhost:8081/actuator/aijob -H 'Content-Type: application/json' -d '{"state":"drain"}'
  kubectl -n nerdnam exec deploy/api -- curl -s localhost:8081/actuator/aijob   # "drained":true 까지 반복
  # 그다음 images.yaml PR merge → nerdnam-apps sync (Recreate). 취소하면 {"state":"resume"}
  ```

  drain 중에는 새 AI 작업만 503으로 거절되고 다른 API는 계속 동작한다(BE #52). 전면 중단은 Recreate 교체 시간(기존 Pod 종료 + 새 Pod 기동·Flyway)뿐이다. 못 끝낸 작업은 종료 때 실패(`INTERNAL`)로 정리되어 사용자가 다시 시도할 수 있다.
- rollback은 `images.yaml`의 이전 digest로 되돌리는 PR이다. DB schema는 되돌아가지 않는다(V6 이전 768차원 앱으로 복귀 불가).
- 자동 sync는 켜지 않았다. FE부터 켜는 것은 배포 후 검증 뒤에 결정한다.
