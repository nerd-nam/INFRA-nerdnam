# 9단계 운영 검증

기준일: 2026-10-29. 상태: **배포 전에 할 수 있는 부분(용량 계산·대시보드·질의 검증·부하 스크립트·시나리오·runbook) 완료. 실제 부하·교체·복구 시험은 배포 후.** 이 문서의 "로컬 확인"은 Docker로 앱·exporter를 띄운 결과이고 클러스터 결과가 아니다.

배포 절차는 [배포-runbook.md](배포-runbook.md)에 모았다.

## 1. 노드 용량 (검증 스크립트 `check_capacity`)

렌더된 모든 Deployment·StatefulSet·DaemonSet과 operator가 만드는 Prometheus·Alertmanager의 requests·memory limit을 역할별 노드에 더해 allocatable **추정값**과 비교한다. EKS add-on Pod(aws-node·kube-proxy·ebs-csi·Pod Identity Agent·CoreDNS·EBS CSI controller)는 렌더 결과에 없어 추정 requests를 더했다.

| 노드 | Pod 수 / maxPods | CPU requests / allocatable | 메모리 requests / allocatable | 메모리 limit 합 |
| --- | --- | --- | --- | --- |
| app (m7i.xlarge) | 11 / 58 | 1.47 / 3.92 | 3.1 / 14.4Gi | 4.1Gi |
| platform (m7i.xlarge) | 25 / 58 | 1.31 / 3.92 | 4.1 / 14.4Gi | 9.5Gi |
| data (m7i.large) | 9 / 29 | 1.30 / 1.93 | 2.8 / 7.0Gi | 4.1Gi |

- 규칙: requests 합 ≤ allocatable의 85%, data 노드는 memory limit 합 ≤ allocatable(DB·Redis가 함께 peak여도 노드 OOM이 없게), Pod 수 ≤ maxPods. requests가 없는 Pod는 실패로 본다.
- allocatable 추정: EKS AL2023 kube-reserved(메모리 255Mi + 11Mi × maxPods, CPU 6%·1%·0.5%·0.5%), eviction 100Mi, OS 메모리는 표기의 96%. maxPods는 VPC CNI 기본(prefix delegation 없음). **배포 후 `kubectl describe node`의 Allocatable로 바꿔 다시 본다.**
- 이 검사로 찾아 고친 것: cert-manager의 cainjector·webhook, external-secrets의 webhook·cert-controller에 requests가 없었다. 스케줄러가 자리를 계산하지 못하고 노드가 붐빌 때 먼저 쫓겨난다. 측정 전 시작값(10~20m / 64~128Mi)을 넣었다.
- 가장 빠듯한 곳은 data 노드 CPU(67%)다. 2 vCPU에 PostgreSQL 750m, Redis 250m, exporter, DaemonSet이 있다. platform 노드는 memory limit 합(9.5Gi)이 allocatable 안이지만 Prometheus WAL·Loki 압축 peak는 실측해야 한다.
- BE 교체(Recreate)는 Pod가 겹치지 않아 추가 자리가 필요 없다. web·ai의 rolling update 1개 추가분은 quota 검사(6단계)가 계산한다.

## 2. 대시보드 (`gitops/observability/dashboards`)

Grafana sidecar가 `grafana_dashboard=1` 라벨 ConfigMap을 읽는다(모든 namespace). ConfigMap은 `monitoring`에 둔다. 화면에서 고칠 수 없게(`editable: false`) 하고 Git JSON을 고친다. kube-prometheus-stack의 기본 대시보드(노드·Pod·PVC 등)는 그대로 쓴다.

| 대시보드 | 내용 |
| --- | --- |
| `nerdnam 서비스` | BE 수집 상태, 요청/초, 5xx 비율, 상태 코드별 요청, 경로별 평균·최대 응답 시간, DB 연결 풀, AI 작업 큐·스레드·진행·실패, 임베딩 대기 수·최장 시간, JVM heap, Pod 메모리·재시작, 오류 로그(Loki, trace_id로 Tempo 이동) |
| `nerdnam 데이터` | PostgreSQL·Redis 상태, DB 크기·연결 사용률·상태별 연결·트랜잭션·잠금·교착, Redis 메모리·명령·연결·오류·AOF, data PVC 사용률, Pod 메모리 / limit |

빠진 것과 이유:

- **p95 응답 시간**: BE가 `http.server.requests` histogram을 내지 않는다(평균·최대만). 필요하면 BE에서 `management.metrics.distribution.percentiles-histogram.http.server.requests=true`를 켜야 한다(지표 수가 경로 × 버킷만큼 는다).
- **Bedrock(모델별 호출·throttle·토큰)**: AI 서버가 아직 지표를 내지 않는다. AI#42 계측이 들어오면 trace에서 먼저 보고, 지표가 생기면 패널을 추가한다.
- **BE → AI 호출(`http_client_requests`)**: AI 호출이 한 번이라도 있어야 생기는 지표라 로컬에서 이름을 확인하지 못했다. 확인 후 추가한다.
- **Argo sync 상태·배포 시각**: Argo CD 지표 수집(ServiceMonitor)을 아직 켜지 않았다.

## 3. 질의 검증

1. **정적(검증 스크립트 `check_queries`, 매번 실행)**: 알림 규칙 11개와 대시보드 PromQL 44개, 합계 55개에서 지표 이름을 뽑아 아래 목록과 대조한다. `namespace`·`job` 짝이 실제 ServiceMonitor와 맞는지, 데이터 소스 uid가 있는지(`prometheus`·`loki`·`tempo`)도 본다.
   - `tests/fixtures/metrics/{api,postgres-exporter,redis-exporter}.txt`: 실제로 수집한 지표 이름. BE `4debdaa`(관리 포트 8081), postgres_exporter v0.20.1, redis_exporter v1.93.0.
   - 클러스터에서만 나오는 지표(kubelet·cAdvisor·kube-state-metrics·`up`)는 스크립트의 `CLUSTER_METRICS`에 이름을 적었다.
   - **앱이나 exporter 이미지를 바꾸면 목록을 다시 수집한다**: 아래 2번처럼 띄우고 `/actuator/prometheus`·`/metrics`의 이름을 저장한다.
2. **실행(로컬, 2026-10-29)**: BE(compose, `MANAGEMENT_PORT=8081`), postgres·redis exporter(배포와 같은 이미지 digest), Prometheus 3.5.0을 띄웠다. 대시보드와 같은 `namespace`·`job` 라벨을 붙여 수집하고 55개 질의를 모두 실행했다.
   - 문법 오류 0. 데이터가 나온 것 40, 비어 있는 것 15. 빈 것은 알림 규칙 10개(조건 미충족이 정상)와 클러스터 지표 5개(cAdvisor·kube-state-metrics·Loki)다.
   - "5xx 비율"은 5xx가 0건일 때 비어 보여서 `or vector(0)`로 0이 보이게 고쳤다.
   - 7단계 알림 규칙이 쓰는 지표 이름도 모두 실제로 있었다.
   - 발동 시험: PostgreSQL·Redis를 멈추자 `NerdnamPostgresDown`·`NerdnamRedisDown` 식이 결과를 냈다.
3. 일부러 틀리게 바꾼 5곳이 모두 걸러졌다: 대시보드 지표 오타, 규칙 지표 오타, 잘못된 job 라벨, app 노드 메모리 초과, cainjector requests 삭제.

## 4. 부하 시험 스크립트 (`scripts/load/read-only.js`, k6)

- **읽기 경로만 부른다.** 분석·가이드 생성은 Bedrock 요금이 들어 부르지 않는다. 로그인 없이: `/`(web), `/api/auth/csrf`, 보호 경로가 401로 빨리 거절되는지. `SESSION` 쿠키를 주면 `/api/me`·`/api/projects`·`/api/job-postings`·`/api/me/library`·`careers`·`skills`.
- 세기: 일정 도착률(`RATE`/초, 기본 2), `DURATION`(기본 2분). 임계값(측정 전 시작값): check 성공률 > 99%, API p95 < 800ms, web p95 < 1.5s.
- 로컬 확인: k6 1.3.0으로 로컬 BE에 실행했다. 처음 실행에서 쿠키 저장소를 초기화 단계에서 만드는 오류를 찾아 고쳤다. 로컬엔 web이 없어 web 검사는 실패하는 게 맞다.
- 배포 후 순서: `RATE=2` 2분 → 대시보드 확인 → `RATE=10` 5분 → app 노드 CPU·BE heap·DB 연결 풀·응답 시간 확인 → 한도가 보일 때까지 올린다. 시험 계정 쿠키는 저장소·채팅에 남기지 않는다.

## 5. 장애·운영 시나리오

"기대"는 설계상 동작이다. "로컬 확인"은 Docker 결과, 나머지는 배포 후 시험한다.

| 시나리오 | 기대 동작 | 보일 신호 | 상태 |
| --- | --- | --- | --- |
| **Redis 중단** | BE readiness 503(약 2초), liveness 200 → Service에서 빠지고 재시작 안 함. 세션이 필요한 요청은 실패 | `NerdnamRedisDown`, 서비스 대시보드 BE 수집 정상·요청 감소, Traefik 503 | **로컬 확인**: Redis를 멈추면 세션 경로가 Redis 명령 timeout(2초 × 여러 번)으로 약 8초 뒤 500을 냈다. 클러스터에선 readiness가 먼저 빠져 사용자는 503을 본다 |
| Redis 복구 | 몇 초 안에 정상 | 위 신호 해소 | **로컬 확인**: 짧은 재시작은 즉시 복구. 약 3분 멈췄다 살리면 BE 재연결까지 약 1분 50초 더 걸렸다(Lettuce 재연결 간격이 늘어난 상태). 그동안 readiness도 503이라 중단이 그만큼 길어진다 |
| PostgreSQL 중단 | DB가 필요한 요청 500, readiness 503(db health) | `NerdnamPostgresDown`, 데이터 대시보드 | 로컬: 발동 식 확인. readiness는 배포 후 |
| BE 교체(이미지 업데이트) | drain → 새 AI 작업만 503, 다른 API 정상 → Recreate 중단(기동 수십 초) → 못 끝낸 작업은 실패(`INTERNAL`)로 정리 | AI 작업 진행 수 0 수렴, 교체 중 BE 수집 down | 배포 후 |
| app 노드 교체 | web·api·ai·Traefik 모두 재배치, NLB 대상 교체 동안 중단 | 노드 NotReady, Pod Pending → Running | 배포 후 |
| data 노드 교체 | 같은 AZ(2c) 새 노드에 EBS 재연결, DB·Redis 중단 후 데이터 유지 | PVC 재연결, `pg_up` 0 → 1 | 배포 후(5단계 보존 시험과 함께) |
| platform 노드 장애 | 관측·Argo·controller 중단. 서비스는 계속(인증서 갱신·Secret 동기화는 멈춤). 내부 Alertmanager도 멈춰 알림이 안 온다 | 클러스터 밖 알림 필요(CloudWatch EC2 상태) | 배포 후. 외부 알림은 미구성 |
| OOM·재시작 | limit 초과 Pod 재시작 | kube-prometheus-stack 기본 규칙(`KubePodCrashLooping` 등), Pod 재시작 패널 | 배포 후 |
| Bedrock 한도 지속 | AI 작업 실패 증가, 큐 적체 | `NerdnamAiJobFailures`·`QueueBacklog`, AI 로그 `bedrock llm … retries` | 배포 후. 시간 상한 불일치는 SPEC#91 |
| Redis 메모리 가득 | noeviction이라 새 세션 쓰기 거절(OOM 오류) | `NerdnamRedisMemoryHigh` → `RejectingWrites` | 배포 후 |
| PVC 공간 부족 | 쓰기 실패 | 기본 규칙 `KubePersistentVolumeFillingUp`, 데이터 대시보드 PVC 사용률 | 배포 후 |

Redis 재연결 지연은 BE 쪽 개선 후보다(Lettuce 재연결 간격 상한 축소, 끊긴 동안 명령을 기다리지 않고 바로 거절). 운영 영향은 "Redis가 오래 멈춘 뒤 복구 때 BE가 최대 약 2분 더 503"이다. 지금은 문서에만 남긴다.
