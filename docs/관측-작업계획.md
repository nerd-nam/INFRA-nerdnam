# 7단계 지표·로그 (Prometheus·Grafana·Loki·Alloy)

기준일: 2026-10-29. 상태: **코드·로컬 검증 완료, 미배포.** "확인함"은 로컬 Helm 렌더링·Terraform mock 테스트·로컬 Docker 실행 결과다. 실제 수집·저장·알림, Pod Identity로 S3 쓰기, NetworkPolicy 허용은 배포 후 검증할 항목이다.

범위 밖: 분산 추적(8단계, [추적-작업계획.md](추적-작업계획.md). Alloy가 OTLP trace도 받는다), 알림 수신 채널(Slack·메일 등 미정), CloudWatch 연계, S3 백업.

## 1. 구성

모두 `monitoring` namespace, **platform 노드**(`workload=platform` + `dedicated=platform` toleration). node-exporter만 모든 노드.

| 구성요소 | 차트(고정 버전) | 저장 | 자원(requests / limit) |
| --- | --- | --- | --- |
| Prometheus | kube-prometheus-stack `92.7.0` (operator v0.94.1) | gp3-retain 30Gi, 보존 7일 + 20GB 상한 | 300m / 1.5Gi, 3Gi |
| Alertmanager | 같은 차트 | gp3-retain 2Gi, 120시간 | 20m / 64Mi, 128Mi |
| Grafana | 같은 차트에 포함(grafana-community 13.6.0) | gp3-retain 5Gi (SQLite) | 50m / 192Mi, 512Mi |
| operator·kube-state-metrics | 같은 차트 | — | 50m / 128Mi · 20m / 64Mi |
| node-exporter | 같은 차트, DaemonSet | — | 20m / 32Mi, 64Mi |
| Loki | grafana/loki `7.3.0` (3.6.12), SingleBinary 1개 | chunk·index **S3**, WAL gp3-retain 10Gi, 보존 7일 | 200m / 512Mi, 1.5Gi |
| Alloy | grafana/alloy `1.13.1` (v1.20.1), Deployment 1개 | `/tmp` emptyDir(읽은 위치) | 100m / 192Mi, 512Mi |
| postgres-exporter | 이미지 `v0.20.1` digest 고정 (data 차트) | — | 50m / 64Mi, 128Mi |
| redis-exporter | 이미지 `v1.93.0` digest 고정 (data 차트) | — | 50m / 64Mi, 128Mi |

- 차트는 2주 이상 된 마지막 안정 버전을 골랐다(2026-10-29 기준). `grafana/grafana` 차트는 grafana 저장소에서 **지원 중단(deprecated)** 이라 따로 쓰지 않고, kube-prometheus-stack이 포함한 grafana-community 차트를 쓴다.
- EKS 관리형 control plane은 etcd·scheduler·controller-manager 지표를 열지 않고, kube-proxy는 127.0.0.1에만 열어 해당 수집·기본 규칙을 껐다(켜 두면 항상 "down" 알림).
- Prometheus·Alertmanager·Grafana·Loki는 공개하지 않는다(ClusterIP, Ingress 없음). 관리자는 `kubectl -n monitoring port-forward svc/grafana 3000:80`.

## 2. 수집 경로

```text
Prometheus ── ServiceMonitor ──> api:8081/actuator/prometheus   (nerdnam, BE 관리 포트)
           ├─────────────────> postgres-exporter:9187, redis-exporter:9121 (data)
           └─ 차트 기본 ───────> kubelet·cAdvisor·node-exporter·kube-state-metrics·Loki·Alloy
Alloy ── Kubernetes API(pods/log, events) ──> Loki:3100 ──> S3 (nerdnam-dev-loki-<계정>-ap-northeast-2)
Grafana ──> Prometheus(기본), Loki(추가 데이터 소스)
```

- **로그 수집 방식 변경**: 구축 계획은 노드별 Alloy DaemonSet이 노드의 로그 파일을 읽는 방식(hostPath, root 권한 필요)이었다. 노드가 3대뿐이라 **platform 노드의 Alloy 1개가 Kubernetes API로 모든 Pod 로그를 읽도록** 바꿨다. hostPath·root 없이 uid 473, 읽기 전용 root로 돈다. Pod 수가 크게 늘면 API 부하를 보고 DaemonSet 방식으로 되돌린다.
- 로그 label: `cluster`, `namespace`, `pod`, `container`, `app`, `node`. `member_id`·작업 id는 label로 만들지 않는다(본문에만). Kubernetes 이벤트도 함께 보낸다.
- Alloy 차트 기본 권한에는 **클러스터 전체 Secret·ConfigMap 읽기**가 들어 있다. 로그 수집에 필요한 `pods`·`pods/log`·`namespaces`·`events` 읽기만 남겼다(검증 스크립트가 막는다). 노드 읽기(cluster rules)는 차트 기본값이다 — 비우면 차트 템플릿이 깨진다.

## 3. 데이터 계층 지표 계정 (5단계 확장)

| 계정 | 권한 | 비밀값 (`nerdnam/dev/data` JSON 키) |
| --- | --- | --- |
| PostgreSQL `nerdnam_exporter` | `pg_monitor`, DB `nerdnam` CONNECT, 연결 3개 상한. 업무 테이블 읽기·DDL 불가 | `postgres-exporter-password` |
| Redis `exporter` | 키 접근 없음. `@connection`, `PING`, `INFO`, `CONFIG GET`, `SLOWLOG GET/LEN`, `LATENCY LATEST/HISTOGRAM`, `CLIENT LIST`, `MEMORY STATS` | `redis-exporter-password` |

- 초기화 스크립트(`postgres-init.sh`)와 Redis 시작 스크립트에 추가했다. **이미 초기화된 DB에는 다시 실행되지 않는다.** 지금은 배포 전이라 해당 없지만, 기존 DB에 추가할 때는 슈퍼유저로:

  ```sql
  CREATE ROLE nerdnam_exporter LOGIN PASSWORD '<postgres-exporter-password>' CONNECTION LIMIT 3;
  GRANT pg_monitor TO nerdnam_exporter;
  GRANT CONNECT ON DATABASE nerdnam TO nerdnam_exporter;
  ```

  Redis는 ACL 파일을 시작 때 만들므로 비밀값을 넣고 Redis Pod를 재시작하면 된다.
- exporter는 data 노드에 두고 Service ClusterIP로 노출한다. 통신 정책: exporter → PostgreSQL 5432 / Redis 6379, Prometheus(monitoring) → exporter 지표 포트만.

## 4. AWS 자원 (Terraform `modules/observability`, 일부 `modules/platform`)

- S3 bucket `nerdnam-dev-loki-<계정>-ap-northeast-2`: 공개 차단, BucketOwnerEnforced, SSE-S3, TLS 아닌 요청 거부, lifecycle 28일 만료(Loki 보존 7일보다 길게 둔 안전망), 미완료 multipart 1일 정리. 버전 관리는 끈다(Loki compactor가 지운 것이 남지 않게).
- 역할 `nerdnam-dev-loki`: Pod Identity로 `monitoring/loki`에만 연결. 그 bucket의 List·Get·Put·Delete만.
- Loki 3.6.12는 AWS SDK Go v2(v1.41)를 써 Pod Identity 자격 증명을 지원한다(go.mod 확인). 정적 키를 넣지 않는다.
- Secrets Manager `nerdnam/dev/monitoring` 메타데이터 추가(값은 Terraform 밖). JSON 키: `grafana-admin-user`, `grafana-admin-password`. ExternalSecret `monitoring/monitoring-secrets`, ESO 읽기 권한·ClusterSecretStore 허용 namespace에 monitoring 추가.
- bootstrap이 AWS state output의 bucket 이름을 `environment.lokiBucket`으로 넘긴다.
- 실행자 IAM 초안: `NerdnamTerraformObservabilityDev`(bucket·Loki 역할), platform 정책에 monitoring Secret 추가.

## 5. 알림 규칙 (`gitops/observability`)

kube-prometheus-stack 기본 규칙(노드·Pod 재시작/OOM·PVC 공간·인증서 등)에 더해:

| 규칙 | 조건 |
| --- | --- |
| `NerdnamApiDown` | BE 지표 수집 5분 실패 |
| `NerdnamAiJobFailures` | 최근 5분 AI 작업 실패 > 3, 10분 지속 |
| `NerdnamAiJobQueueBacklog` | AI 작업 큐 > 50, 10분 |
| `NerdnamEmbeddingStuck` | 임베딩 대기 최장 > 30분 |
| `NerdnamPostgresDown`, `NerdnamPostgresConnectionsHigh` | 접속 불가 2분 / 연결 > 80% |
| `NerdnamRedisDown`, `NerdnamRedisMemoryHigh`, `NerdnamRedisRejectingWrites`, `NerdnamRedisAofWriteFailed` | 접속 불가 / 메모리 > 80% / OOM 거부 / AOF 실패 |
| `NerdnamLokiDown` | Loki 수집 10분 실패 |

- 임계값은 실측 전 시작값이다. **수신 채널이 없어 지금은 Alertmanager UI에서만 보인다**(`null` receiver). 채널이 정해지면 Secret으로 넣는다.
- AI 서버는 아직 Prometheus 지표를 내지 않는다(AI#42 계측 이슈에 Bedrock 호출 속성으로 요청). AI 호출 지연·한도 초과는 지금 로그(`bedrock llm … wait=… retries=…`)로 본다.

## 6. 배포 순서 (사용자가 실행)

1. AWS 루트 apply(`modules/observability`) → bootstrap apply(seed 갱신).
2. `nerdnam/dev/monitoring`, `nerdnam/dev/data`의 exporter 키 2개 공급.
3. 수동 sync: foundation(monitoring namespace) → secrets → kube-prometheus-stack(CRD Ready 확인) → loki → alloy → data(exporter) → apps(BE 관리 포트 정책) → observability(ServiceMonitor·규칙).
4. 확인: Prometheus targets(api·exporter·Loki·Alloy up), Grafana에서 Loki 로그 조회, S3에 chunk 생성, 알림 규칙 로드.

## 7. 검증 결과

로컬(2026-10-29):

- `scripts/validate_gitops.py`: 자체 chart 8개, 공식 chart 8개(3개 추가, SHA256 확인), CR 27개 CRD schema(ServiceMonitor·PrometheusRule 포함), 기본 객체 52개 1.35 엄격 검사, upstream 배치 22개. 관측 검사: Prometheus·Alertmanager CR까지 platform 배치, PVC gp3-retain, 보존값, Grafana 관리자 비밀번호가 Secret에서 옴, node-exporter 모든 노드, Ingress 없음, Loki SingleBinary·S3·정적 키 없음·SA 이름, Alloy RBAC에 Secret·ConfigMap 없음·hostPath 없음, **ServiceMonitor → Service(라벨·포트 이름) → NetworkPolicy(Prometheus 허용)** 연결이 실제로 맞는지.
- Terraform mock 테스트 14개(observability 1개: bucket 공개 차단, lifecycle > 보존, Pod Identity 대상, 자기 bucket만), bootstrap 1개(lokiBucket 전달).
- 로컬 Docker:
  - 렌더된 PostgreSQL 초기화 스크립트로 `nerdnam_exporter` 생성, postgres-exporter(uid 65534, 읽기 전용) `pg_up 1`, exporter 계정의 테이블 생성 거부.
  - 렌더된 Redis ACL로 redis-exporter(uid 59000) `redis_up 1`, 권한 오류 없음(처음엔 `LATENCY HISTOGRAM`이 막혀 추가), exporter 계정의 `GET`·`KEYS`·`ACL LOG` 거부.
  - 렌더된 Alloy 설정을 `alloy fmt`로 문법 확인, uid 473·읽기 전용 root로 실행해 Kubernetes 접속 전 단계까지 설정 평가(클러스터가 없어 in-cluster 설정 오류로 끝나는 것은 예상대로).
- 로컬 PyYAML이 prometheus-operator CRD의 `=` 값을 YAML 1.1 태그로 읽어 실패해서, 검증 스크립트의 loader가 문자열로 읽게 했다.

배포 후 검증할 것: 모든 수집 대상 up, Loki가 Pod Identity로 S3에 쓰기, 7일 뒤 compactor 삭제, Grafana 로그인(ESO 비밀값), NetworkPolicy 허용·차단, platform 노드 메모리 여유(Prometheus WAL·Loki), node-exporter가 세 노드 모두에 뜨는지.
