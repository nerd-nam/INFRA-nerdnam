# 부하 시험 실행 (scripts/load-test.sh)

기준일: 2026-11-03. 부하 시험 smoke·rate·concurrency 를 **명령 하나로** 돌린다. 시험 구조·대시보드 설계·검증 기록은 [부하-시험.md](부하-시험.md).

```sh
scripts/load-test.sh run smoke          # 2분, 배포 직후 경로 확인
scripts/load-test.sh run rate           # 약 6분, 초당 요청량을 올린다
scripts/load-test.sh run concurrency    # 약 6분, 동시 사용자를 올린다
```

시작 전 확인 → 시험 내용 보여 주고 확인 → 진행 표시 → k6 요약 → Grafana 링크 → 정리까지 한 번에 한다.

## 1. 시험 종류

| 시험 | 무엇을 보나 | 기본 단계 | 시간 |
| --- | --- | --- | --- |
| `smoke` | 배포 직후 경로가 정상인지 | 초당 반복 2회 고정(초당 요청 약 6) | 2분 |
| `rate` | 초당 N건이 들어오면 버티는가. 서버가 느려져도 k6 가 작업자를 늘려(최대 500) 요청량을 유지한다 | 초당 반복 25 → 50 → 100 → 150 (마지막은 초당 요청 약 450) | 약 6분 |
| `concurrency` | 사용자 N명이 동시에 쓰면 어떤가. 각 사용자는 한 바퀴 돌고 0.5초 쉰다. 서버가 느려지면 요청량도 줄어든다 | 동시 사용자 50 → 100 → 200 → 300 | 약 6분 |

- 반복 1번 = `/`(web) + `/api/auth/csrf` + `/api/projects`(비로그인 401). `--session` 을 주면 로그인 경로 6개(`/api/me` 등)를 더 부른다.
- 단계마다 20초 올리고 1분 유지한다. 대시보드는 최근 1분 평균이라 **유지 구간 끝 무렵 값**을 읽는다.
- AI 기능(Bedrock)은 부르지 않는다(요금).
- 권장 순서: `smoke` → `rate` → `concurrency`. 결과를 보고 한도 근처를 `--stages` 로 다시 잰다.

## 2. 준비

```sh
cd ~/project/nerdnam/INFRA-nerdnam
git switch main && git pull --ff-only    # 시험 파일(gitops/load/testruns)을 최신으로
scripts/cluster.sh status                # 꺼져 있으면 scripts/cluster.sh up
```

- **사용자가 없는 시간**에 돌린다. rate·concurrency 마지막 단계는 일부러 서버 한계를 넘긴다.
- 필요한 도구: `kubectl`(컨텍스트 `nerdnam-dev`), `jq`, `git`. 관리 IP 에서 실행한다.

## 3. 명령

### run — 시험 하나 돌리기

```sh
scripts/load-test.sh run <smoke|rate|concurrency> [옵션]
```

| 옵션 | 뜻 |
| --- | --- |
| `--stages "<목표:시간,...>"` | rate·concurrency 단계 바꾸기. rate 는 초당 반복 수, concurrency 는 동시 사용자 수. 예: `"80:20s,80:1m,100:20s,100:1m,0:20s"` |
| `--session` | 로그인 경로까지. 시험 계정 `SESSION` 쿠키를 입력받아(화면에 안 보임) Secret 으로 넣고, 끝나면 지운다 |
| `--keep` | 끝난 뒤 TestRun 을 지우지 않는다(로그를 더 볼 때. 나중에 `stop` 으로 정리) |
| `--dry-run` | 만들 TestRun 을 클러스터에서 검사만 하고 끝낸다. **부하 없음** |
| `-y` | 시작 전 확인을 묻지 않는다 |

진행 순서:

1. **확인**: 클러스터 접속, 노드 3대 Ready, k6-operator·ConfigMap 준비, **도는 시험이 없음**(있으면 중단). 끝난 시험은 지운다. 로컬 시험 파일이 origin/main 과 다르면 경고.
2. **시험 내용**: 대상 주소, 단계, 예상 시간, 로그인 경로 포함 여부 → `시작할까요? [y/N]`
3. **진행**: `initialization → created → started → finished` 를 시간과 함께 출력. **Ctrl+C 를 누르면 시험도 멈추고 지운다.**
4. **k6 요약**: runner 로그 마지막 부분(요청 수, 응답 시간, 실패, threshold)
5. **Grafana 링크**: 이 시험(TestRun 이름, 예: `rate-bpjnp`)과 시간 범위가 맞춰진 "nerdnam 부하 시험" 대시보드 주소
6. **정리**: TestRun·Secret 삭제(지표는 Prometheus 에 7일)

예:

```sh
scripts/load-test.sh run smoke -y
scripts/load-test.sh run rate --stages "80:20s,80:1m,100:20s,100:1m,120:20s,120:1m,0:20s"
scripts/load-test.sh run concurrency --session
scripts/load-test.sh run rate --dry-run            # 부하 없이 검사만
```

`--stages` 규칙: 단계마다 `올리는 구간,유지 구간` 두 개, 마지막은 `0:20s`(내리기). **유지 구간은 1분 이상**(짧으면 앞 단계 값이 섞인다).

### status · logs · stop

```sh
scripts/load-test.sh status        # 시험·Pod·quota(Used/Hard)
scripts/load-test.sh logs [이름]    # k6 요약. 이름이 없으면 가장 최근 시험(--keep 로 남긴 것)
scripts/load-test.sh stop          # 모든 시험을 멈추고 지운다(+ 쿠키 Secret). 서비스가 이상할 때 바로 쓴다
```

## 4. 결과 읽기 (Grafana "nerdnam 부하 시험")

run 이 마지막에 낸 링크를 연다. 직접 열 때는 위쪽 **시험** 에서 TestRun 이름(`rate-xxxxx`·`concurrency-xxxxx`, **최근에 끝난 시험이 위**)을 고르고 시간 범위를 시험 시작~끝으로 맞춘다. 대시보드는 30초마다 새로 고친다.

| 줄 | 볼 것 |
| --- | --- |
| 부하 (k6) | k6 요청/초, **p95(최근 1분, web·api)**, 실패 비율, 동시 사용자 수(concurrency) 또는 응답 대기 중인 작업자(rate·smoke), **못 보낸 반복**, k6 Pod CPU |
| 서버 응답 (BE) | BE 요청/초(상태별), BE p95(경로별), DB 연결 풀 대기 |
| 자원 사용량 | 노드 CPU·메모리(역할별), Pod CPU·메모리 / limit, JVM heap, PostgreSQL 연결·커밋, Redis 명령·연결 |

**한도 판단(시작값)** — 아래 중 하나가 유지 구간 1분 내내 이어지면 그 단계를 한도로 본다.

- API p95 > 800ms 또는 web p95 > 1.5초
- 실패 비율 > 1%
- app 노드 CPU > 80%
- Pod 메모리 / limit > 90%
- DB 연결 대기 > 0

**부하 발생기 한계와 구분**: "못 보낸 반복"이 생기거나 k6 Pod CPU 가 계속 높으면 k6 쪽 한계다. 그 구간은 서버 한도로 보지 않는다. rate 에서 "응답 대기 중인 작업자"가 늘기 시작하면 서버가 느려지는 신호다.

BE 지표는 30초 간격이라 k6 그래프(5초)보다 늦게 따라온다. 시험 중 `NerdnamApiLatencyHigh` 등 알림이 울릴 수 있다(정상).

## 5. 문제 해결

| 메시지 | 원인·해결 |
| --- | --- |
| `클러스터에 닿지 않습니다` | 노드가 꺼짐 → `scripts/cluster.sh up`. 관리 IP 가 바뀜 → [운영-중지-재개.md](운영-중지-재개.md) 4절 |
| `다른 시험이 진행 중입니다` | 한 번에 하나만 돈다. 끝날 때까지 기다리거나 `scripts/load-test.sh stop` |
| `quota 에 막혔습니다(exceeded quota)` | 시험 두 개가 겹쳤다(quota CPU 800m 는 runner 하나만 들어간다). `status` 로 확인 후 `stop` |
| `시험이 실패했습니다(error)` | 출력된 initializer·runner 로그를 본다. 스크립트 오류(`BASE_URL`·`STAGES`·`SCENARIO`)는 대부분 initializer 에서 난다 |
| `예상 시간보다 5분 넘게 끝나지 않아 멈췄습니다` | runner 가 멈췄거나 이미지 받기가 오래 걸림. `kubectl --context nerdnam-dev -n load-test get pods,events` |
| `로컬 … 이 origin/main 과 다릅니다` (경고) | `git pull` 을 안 했거나 파일을 고친 상태. 의도한 수정이면 그대로 진행 |
| 대시보드 p95 가 비어 있음 | k6 가 응답 시간을 native histogram 으로 보내는지(#9). k6 요청/초는 나오는데 p95 만 비면 Prometheus 수신 문제 |

## 6. 비용·영향

- 부하는 클러스터 안 k6(platform 노드) → NAT → 공인 NLB → Traefik 으로 들어온다. NAT 데이터 처리 요금이 붙는다(시험 하나에 수백 MB~수 GB).
- k6 runner 는 CPU 상한이 없어 platform 노드의 Prometheus·Grafana 와 CPU 를 나눠 쓴다. k6 Pod CPU 패널이 계속 1코어 근처면 runner 요청을 올리고 quota 도 함께 올린다(검증 스크립트가 "runner 두 개는 넘친다"를 확인).
- 다 끝나면 `scripts/cluster.sh down` 으로 노드를 내린다.
